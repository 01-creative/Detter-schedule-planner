# Detter · 产品与系统总览

> 一句话：**把"当时觉得记一下就行、后来一定忘"的小事，用 3 秒捕获住，并自动挂到长期目标上。**

---

## 1. 要解决的真实问题

用户（甲方）的原始痛点，逐条对应到设计决定：

| 真实痛点 | 设计回应 | 落地模块 |
| --- | --- | --- |
| 消息、地址、日期、课程作业，当时几分钟记得，一忙就忘 | 全局 3 秒捕获：快捷键 / 手机主屏 / 系统分享菜单，先落收件箱再慢慢整理 | 快速捕获 + 收件箱 |
| 记了但"懒"得再去整理 | 捕获即解析（时间、地点、标签、目标），默认值合理，一键确认；AI 可批量整理 | NLP 解析 + AI 分诊 |
| 小事和长期目标脱节 | 每个任务可挂 Goal / OKR-KR，目标栏常驻右侧 | 目标栏 + OKR |
| 不知道今天该干什么 | 四象限首页：重要/紧急两轴，拖一下就能定位 | 四象限画布 |
| 定了目标落不到日常 | 目标 → 一键铺成任务；周期性目标按 RRULE 自动出现 | Goal + 重复规则 |
| 时间投入没有反馈 | 番茄钟与任务绑定，自动汇总成 KPI（深度工作时长） | 番茄钟 + KPI |
| 想让 AI 帮忙管，但不想被平台绑死 | 对外暴露 REST + MCP，用带 scope 的 API Key，任何 agent 都能读写 | AI 接口层 |

**非目标（明确不做）**：团队协作、多人共享、企业审批流、社交、复杂项目管理（甘特图/资源排期）。

## 2. 核心闭环

```
         ┌──────────── 3 秒捕获（任何入口）────────────┐
         │                                            │
         ▼                                            │
     [ 收件箱 Inbox ] ──分诊──► [ 四象限 / 日历 ] ──► [ 番茄钟执行 ]
         │                         ▲                        │
         │                         │                        ▼
         └──── AI 自动整理 ────────┘                  [ KPI / 统计 ]
                                   ▲                        │
                                   │                        ▼
                            [ 目标 / OKR ] ◄────── [ 周月复盘 ]
```

设计上的三个硬约束：
1. **捕获必须比遗忘快**：任何一次记录 ≤ 3 秒、≤ 2 次点击、离线可用。
2. **首页必须能回答"现在做什么"**：四象限是默认落地页，不是仪表盘。
3. **数据必须能带走**：本地 IndexedDB 为第一副本，服务端可换、可导出、可给 AI。

## 3. 模块地图

| 模块 | 路由 | 主要能力 | 数据 |
| --- | --- | --- | --- |
| 四象限（首页） | `/` | 2×2 画布、右键新建、拖拽换象限/定位、精确坐标、按目标着色 | task |
| 目标栏 | 右侧常驻 | 一次性/周期/模板三类目标；拖到象限即建任务；模板一键铺开 | goal |

| 日历 | `/calendar` | 日/周/月视图、任务与事件同轴、拖拽改期、重复实例 | task |
| OKR | `/okr` | 周/月/季目标、KR 量化、进度联动任务与目标 | okr, kr |

| 设置 | `/settings` | 同步状态、设备、推送、API Key、外观、导入导出 | setting, device |

## 4. 技术选型与理由

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 前端框架 | React 19 + TypeScript + Vite | 生态最稳，团队/子代理都熟；Vite 启动快 |
| 样式 | Tailwind CSS v4 + CSS 变量令牌 | v4 的 `@theme` 让令牌即样式，零运行时 |
| 动画 | Motion（framer-motion 继任者） | 手势 + 布局动画强，API 稳定 |
| 本地库 | IndexedDB + Dexie | 事务、索引、订阅式查询（useLiveQuery） |
| 状态 | Zustand（UI 状态）+ Dexie（领域数据） | 职责分离：不把服务端数据塞进 store |
| 渲染 | Canvas 无关（DOM + transform） | 四象限/导图用 DOM 更易做无障碍与文本选择 |
| 后端 | Hono（运行时无关） | 同一份代码跑 Workers 与 Node，零锁定 |
| 数据库 | SQLite 方言：D1 / node:sqlite | 单人数据量（万级行）完全够；迁移成本为零 |
| 同步 | 自研 op-log + 增量拉取 | 单人场景不需要 CRDT 的复杂度，可解释性优先 |
| AI | REST + MCP + 上下文包 | 不绑定模型，任何 agent 都能接管 |

**明确不引入**：GraphQL、微服务、Redis、Kafka、ORM 重框架、组件库（自建设计系统保证审美一致）。

## 5. 部署形态（双运行时）

```
                  ┌───────────── 方案 A：Cloudflare ─────────────┐
  浏览器/PWA ──►  │  Workers（Hono）+ 静态资源 + D1 + Cron        │
                  └──────────────────────────────────────────────┘
                  ┌───────────── 方案 B：自有服务器 ─────────────┐
  浏览器/PWA ──►  │  Node 24（同一份 Hono 代码）+ node:sqlite     │
                  │  可放在内网，用 Cloudflare Tunnel 暴露        │
                  └──────────────────────────────────────────────┘
```

两套 runtime 共用 `apps/api/src/app.ts`，只有 DB 适配器与推送实现不同。
**这是刻意的**：大陆网络访问 Cloudflare 不稳，用户随时可以搬回自己的服务器，业务代码零改动。

## 6. 质量红线

1. `pnpm verify`（typecheck + lint + test + build）必须全绿才能合并。
2. 同步逻辑必须有单测覆盖冲突、墓碑、幂等三种情况。
3. 任何写入 API 必须经过 zod 校验；任何读取 API 必须校验归属。
4. 前端不得直接拼 SQL / 调第三方 API；所有外部调用走服务端。
5. 每个模块必须有空态、加载态、错误态三种 UI。
