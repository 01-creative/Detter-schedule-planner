## ADR-0001 本地优先 + op-log 同步

**背景**：用户在地铁/教室等弱网环境要能记录；多设备要能同步；单人使用。

**选项**
1. 纯云端（每次操作打接口）——弱网直接不可用，违背核心痛点。
2. 纯本地 + 手动导入导出——跨设备体验差。
3. 本地为第一副本 + outbox + 增量同步——复杂但体验最好。

**决定**：方案 3。IndexedDB 为读写入口，outbox 记录变更，服务端 changes 表做游标。

**后果**：需要认真处理冲突与墓碑；换来了离线可用、跨设备准实时、数据可导出。

## ADR-0002 双运行时

**背景**：用户在中国大陆，Cloudflare 的可用性不稳定；但用户又有一台内网服务器。

**决定**：业务代码与 Hono 应用层完全运行时无关，只把「数据库适配器」「推送实现」抽象成接口。
Workers 用 D1，Node 用 `node:sqlite`（Node 24 内置，零原生依赖）。

**后果**：两种部署都能跑；测试用内存 SQLite，速度快且真实。
代价：不能用 D1 特有的能力（如 `batch` 之外的事务语义），写操作要设计成幂等。

## ADR-0004 四象限双模式

**背景**：用户既要「像待办清单一样好用」，又要「像白板一样能摆位置、能设精确坐标」。

**决定**：同一份数据（`posX/posY` + `sortIndex`），两种渲染：
- 列表模式：流式排序，适合日常处理；
- 自由模式：绝对定位，适合规划与空间记忆。
默认列表，切换全局，坐标始终保留。

**后果**：实现两套布局，但数据模型只有一个，切换无成本。

## ADR-0005 AI 接入方式

**背景**：用户明确表示「先让外部 agent 能通过密钥处理，同时允许导出给 AI；原生 AI 功能后置」。

**决定**：先做 API Key + REST v1 + MCP server + 上下文包导出；内置聊天助手留到 v2。

**后果**：需要认真的密钥与 scope 设计、审计日志；换来的是不被任何模型/平台绑定。
